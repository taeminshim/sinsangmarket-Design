# 신상마켓 화면 제작 길잡이

신상마켓 **디자인 시스템과 UI Builder로 Figma 화면을 그릴 때의 기준**이다.
`references/` 문서를 전부 읽고 시작하지 않는다. 문서를 계속 읽으면 시간과 토큰만 든다 — **기획에서 필요한 요소만 뽑고, 그 요소에 해당하는 파일만** 연다.
피그마 디자인 시스템이 원본이고, 이 문서는 길잡이다. 컴포넌트 정의(variant·속성)는 항상 Figma에서 직접 확인한다.

Figma 작업은 Figma MCP(`use_figma` 등)로 한다. 해당 Figma 스킬(`figma-use` 등)이 있으면 함께 따른다.

## 그리기 전

- **원본 찾기는 먼저 묻는다.** "만들어줘"를 받으면 바로 찾지 않고 "as-is 원본을 찾아서 할까요?"라고 묻는다. 원본 찾기는 시간과 토큰이 많이 든다. 찾으라고 하면 `references/README.md`의 "as-is 원본 화면 찾기"를 따른다.
- 기획서에 예시 이미지가 있으면 먼저 본다.

## 작업 순서

1. **기획 읽기** → 화면에 들어갈 요소 목록을 먼저 뽑는다 (예: 상단바, 입력창 4개, 안내 박스, 하단 버튼).
2. **원본 화면이 있으면 그걸 쓴다.** 원본을 복제해서 그 안의 컴포넌트를 그대로 고쳐 쓴다. 새로 불러오지 않는다.
   - 다른 파일의 화면은 API로 복사할 수 없다. 사용자에게 작업 파일에 원본 프레임을 붙여넣어 달라고 하고, 붙여넣은 것을 복제해서 쓴다.
3. **추가로 필요한 것만 가져온다.**
   1. 키 표에 있으면 바로 불러온다. 이 키들은 확인된 것이다. 키 표는 팀원들이 수시로 추가하므로 **아래 "키 표는 최신본으로 읽기"대로 GitHub 최신본을 읽는다.**
   2. 없으면 `includeLibraryKeys`로 신상마켓 라이브러리 4개(`references/libraries.md`)로 좁혀 그 컴포넌트 하나만 검색하고, 시스템에서 직접 variant·속성을 확인해서 쓴다. 조직에 다른 라이브러리(신상애드 등)가 많아서 범위를 안 좁히면 엉뚱한 게 섞인다.
   3. 처음 쓰는 키는 `references/libraries.md`의 "가이드 페이지 확인" 스크립트로 가이드 페이지(`0:1`)에 있는지 확인한다.
   4. 원본 안 컴포넌트가 다른 파일로 불러와지지 않으면 디자인 시스템 컴포넌트로 다시 조립한다.
   5. 디자인 시스템에도 빌더에도 없으면 커스텀으로 만들고 이름 앞에 `❤︎`를 붙인다. 팀에 공유하라고 알린다.
4. **참고 파일은 막힐 때만** 해당하는 것 하나를 연다.

| 막힌 것 | 참고 파일 |
|---|---|
| 라이브러리 key, 화면 폭·그리드·여백 | `references/libraries.md` (모바일/PC 해당 부분만) |
| 색·글자·라운드·그림자 스타일 이름 규칙 | `references/design-system/foundations.md` |
| 어떤 컴포넌트를 골라야 할지 (버튼·칩·태그·폼·모달) | `references/design-system/components.md` (쓰는 종류만) |
| 자주 쓰는 컴포넌트·스타일 key | 아래 "키 표는 최신본으로 읽기" |
| 상품·매장 썸네일, 빌더 블록 | `references/builder/mobile.md` (PC는 `references/builder/pc.md`) |
| 원본 없이 배치·입력 화면 시작 | `references/builder/templates.md` |
| 다 그린 뒤 검수 | `references/design-system/audit.md` |
| as-is 원본 찾기, Figma 바로가기 링크 | `references/README.md` |

### 키 표는 최신본으로 읽기

키 표는 스킬을 다시 배포하지 않아도 팀원이 추가한 키가 바로 쓰이도록 GitHub에서 최신본을 읽는다. 작업당 한 번, 쓰는 플랫폼 것만 읽으면 된다.

- 모바일: https://raw.githubusercontent.com/taeminshim/sinsangmarket-Design/main/design-system/keys-mobile.md
- PC: https://raw.githubusercontent.com/taeminshim/sinsangmarket-Design/main/design-system/keys-pc.md

웹 가져오기가 안 되면(꺼져 있거나 실패) 스킬에 같이 들어 있는 `references/design-system/keys-mobile.md` · `keys-pc.md`를 쓴다. 이건 스킬을 만든 시점의 사본이라 최근에 추가된 키가 빠져 있을 수 있다고 사용자에게 한 줄 알린다.

## 그릴 때

- **디자인 시스템 먼저, 빌더는 그다음.** 디자인 시스템에 없을 때만(상품·매장 썸네일 등) 빌더에서 가져온다.
- **컴포넌트는 기능을 보고 고른다.** 넣을 수 있다고 넣지 않는다. 예: 여러 항목에 걸친 안내는 입력창 helper text가 아니라 `notice` 박스.
- 색·글자·그림자는 값을 직접 넣지 않고 스타일을 연결한다.
- 디자인 시스템 컴포넌트는 해제(detach)하지 않는다. 컴포넌트·레이어 이름은 바꾸지 않는다.
- variant를 먼저 바꾸고, 글자는 그다음에 넣는다 (variant를 바꾸면 안쪽 텍스트가 새로 갈린다).
- ⚠️ 미게시 표시가 있는 빌더 컴포넌트는 key로 불러오면 실패한다. 표에 적힌 대체 컴포넌트를 쓴다.
- 원본을 찾았으면 원본과 수정안을 나란히 두고, 원본 링크는 `[AS-IS]` 타이틀에 건다 (`references/README.md`). 원본 없이 먼저 그린 초안은 비교용으로 지우지 않는다.
- **디자인 시스템은 각 파일의 가이드 페이지(`0:1`)에서만 가져온다.** 다른 페이지는 테스트·예전 페이지다.
  - 모바일: `❖ [M] Design system Guide_V1.4` (https://www.figma.com/design/5WsL9kg8fteVvSDUw4L1s6?node-id=0-1)
  - PC: `❖ [PC] Design system Guide_V1.4` (https://www.figma.com/design/hzFtDckwBKxfz3QQBrOnHa?node-id=0-1)
  - 모바일 테스트 페이지에는 이름이 똑같은 컴포넌트가 있어서 이름만으로는 못 거른다. PC에서 `Buttons/…`, `bt_…`처럼 이름 규칙(`{종류}{스타일}{사이즈}{번호}`, 예: `btnFilledLarge01`)에 안 맞는 것은 바로 버린다.
- 라이브러리 원본 파일(디자인 시스템·빌더 4개)에는 그리지 않는다.

### 화면 기본값 (자세한 건 `references/libraries.md`)

- **모바일**: 폭 375 (iOS 375×812), 좌우 16 → 콘텐츠 343, 4컬럼·거터 8, 간격 4px 단위. AOS 화면은 따로 그리지 않는다.
- **PC**: 기준 1440, 콘텐츠 프레임 1200(좌우 32 → 1136). GNB → (Breadcrumb) → 지면 → FNB. 1200·2000은 꼭 필요한 화면만, 해상도는 `Size` variant로 맞춘다.

## Figma 작업 팁 (그동안 겪은 오류)

- 컴포넌트를 처음 쓸 때는 바로 넣지 말고 variant 이름과 속성부터 확인한다. 한 호출이 실패하면 그 호출의 수정이 전부 취소된다.
- 글자를 바꾸기 전에 그 텍스트의 폰트를 먼저 불러온다.
- 텍스트는 "자동 높이"를 먼저 설정하고 글자를 넣는다. 그 뒤에 크기를 다시 고정하면 줄바꿈이 깨진다.
- 한 번 실행할 때 페이지 전환은 한 번만 한다.
- 새 요소는 화면 프레임 안에 바로 만든다. 오토레이아웃 안 요소는 좌표가 아니라 간격 값으로 조정한다.
- 해제(detach)한 직후 같은 호출에서는 안쪽 텍스트를 못 찾을 수 있다. 호출을 나눈다.

## 다 그린 뒤

- `references/design-system/audit.md`의 검수 스크립트를 실행해 하드코딩 색·글자, 해제된 시스템 컴포넌트, 다른 라이브러리 컴포넌트를 고친다.
- 스크린샷으로 확인하고, 일부만 했으면 한 것과 남은 것을 나눠 보고한다.
- 기획에 없는 정책은 지어내지 않고 질문으로 남긴다.
- 키 표에 없는 컴포넌트를 썼고 다른 화면에서도 자주 쓸 것 같으면 아래 "키 표에 추가하기"를 한다.

## 키 표에 추가하기

팀원은 대부분 데스크톱 앱에서 쓰고 git을 다루지 않는다. 그래서 클론·pull 없이 **GitHub 파일 하나만 고치는** 방식으로 한다.

1. **먼저 묻는다.** 키 표에 없는 컴포넌트·스타일 목록을 보여주고 "키 표에 추가할까요?"라고 묻는다. 묻지 않고 올리지 않는다.
2. **확인한다.** 추가할 키를 실제로 한 번 불러와 되는지, 가이드 페이지(`0:1`) 것인지 확인한다. 방금 읽은 최신 키 표에 이미 같은 이름이 있으면 새 줄을 만들지 않고 그 줄을 고친다.
3. **줄을 만든다.** 모바일은 `design-system/keys-mobile.md`, PC는 `design-system/keys-pc.md`의 맞는 표(세트·단일·색·텍스트) 형식에 맞춰 줄을 만든다. 막혔던 점이 있으면 같은 파일 "쓸 때 주의" 표에 한 줄 더한다 (특정 화면에서만 쓰는 내용은 넣지 않는다).
4. **올린다.**
   - GitHub에 쓰기 가능한 도구(커넥터 등)가 연결돼 있으면, 그 파일의 최신본에 줄을 넣어 `main`에 바로 커밋한다. 메시지는 `키 추가(MO|PC): 컴포넌트 이름`.
   - 없으면 사용자에게 **어느 표 아래에 붙일지와 붙여넣을 줄**을 코드 블록으로 주고, 편집 링크를 건넨다. 사용자는 링크를 열어 줄을 붙여넣고 "Commit changes"만 누르면 된다 (팀원은 저장소 협업자라 바로 커밋된다). 커밋 메시지 칸에 넣을 `키 추가(MO|PC): 컴포넌트 이름`도 같이 준다.
     - 모바일: https://github.com/taeminshim/sinsangmarket-Design/edit/main/design-system/keys-mobile.md
     - PC: https://github.com/taeminshim/sinsangmarket-Design/edit/main/design-system/keys-pc.md
5. 커밋되면 다른 팀원도 다음 작업부터 바로 쓴다 (키 표는 최신본을 읽기 때문). 스킬을 다시 배포할 필요는 없다.
